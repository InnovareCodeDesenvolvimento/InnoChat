# Revisão de segurança v1.7.2 (f32fa0d..d08feca)

Veredito: LIBERA. 0 críticos, 2 importantes, 3 sugestões. Revisão por leitura do diff; nada foi executado.

## IMPORTANTE
1. `src/modules/platform-whatsapp/connections.ts` (`ensureActiveWebhook`, ramo de rotação): `findWebhook` é SUPOSIÇÃO sobre o formato da Evolution (`evolution-client.ts`). Se a resposta vier num formato que o parser lê como `null` (sem `url` string e sem `enabled`), toda rodada do tick conclui "missing" e GIRA o token de novo: o endereço antigo fica 404 a cada rodada e eventos caem na janela entre o `updateMany` e o `setWebhook`. Correção: limitar a rotação (ex.: no máximo 1 por hora, usando `webhookRepairedAt` do diagnóstico) e, em `info === null`, preferir reaplicar sem girar quando não houver prova de token estranho. Conferir no Evolution real o retorno de `GET /webhook/find` antes/logo após publicar.
2. Mesmo ponto, rollback: se `setWebhook` estoura prazo mas a Evolution aplicou o endereço novo, o `catch` devolve o hash antigo e o webhook aponta para um token sem hash (todas as chegadas dão 404). Autocura na próxima rodada (nova rotação), então a janela é o intervalo do tick. Aceitável; documentar, ou conferir com `findWebhook` antes de restaurar o hash.

## SUGESTÃO
3. `webhook.ts` (decisão de resposta): checagem do teto (`recentAutoreplyTimes`) e gravação da reserva não são atômicas; duas entregas simultâneas do mesmo contato podem responder duas vezes. Dano baixo (a dedup por mensagem barra o reenvio comum). SAIR/SIM exatos têm teto de 30/dia: só quem digita a palavra exata dispara, e o texto do nosso aviso não é igual a ela, então não há eco com outro robô. Teto normal 6/dia e 10 min por contato está coerente. Não existe teto global por hora para o chip (muitos contatos diferentes), igual ao comportamento anterior.
4. `src/core/bot/evolution-normalize.ts`: `resolveSenderIdentity` só usa `altJid` quando o `jid` é `@lid`; `pickPhoneJid` recusa `@lid`, exige 8 a 20 dígitos e sufixo `@s.whatsapp.net`. O remetente não controla esses campos (vêm do servidor do WhatsApp via Evolution, autenticada pelo token do webhook), então não há forja de identidade. Efeito colateral a observar: contato do bot que antes só tinha LID agora resolve para o telefone (`claim.ts:162-195`); se um contato legado tinha `waJid` diferente do telefone resolvido, o upsert por `waJid` cria outro contato com o mesmo `lid`. Verificar se há unicidade de `lid` por empresa; hoje o risco é de duplicata, não de vazamento entre empresas.
5. `extension-noise.ts`: só descarta o stack quando TODA URL é de esquema de extensão. Um atacante que controla o relato (rota pública) pode esconder o próprio erro com um stack de extensão forjado, mas isso só silencia relatos que ele mesmo envia; não esconde erro real de outros usuários.
